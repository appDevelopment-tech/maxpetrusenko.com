Your AGENTS.md Was Written for a Worse Model

GPT-6 Astra exposes a new kind of technical debt: instructions that survived the problems they were meant to fix.

Every instruction in your AGENTS.md was written to fix a real failure. When the model improves, the failure can vanish while the rule survives. That is prompt debt: a behavioral compensation promoted into permanent policy. The fix is a narrower job for the file, combining invariants, hidden constraints, and permission boundaries with a definition of done.

Every time a coding agent fails in a memorable way, somebody adds a rule. It edits too much, so AGENTS.md says to touch only necessary files. It skips verification, so another line says to always run the full test suite. It changes a dependency without asking, so dependency changes become approval-only. It wanders through the repository, so you prescribe exactly which documents it must read first.

Each rule was reasonable when written.

Then the model changed.

``text OLD: Read A → Edit B → Test C NEW: Boundaries → Permissions → Definition of done ``

GPT-6 Astra is substantially better at following instructions than previous coding models, and that improvement changes the economics of prompting. A weaker model may ignore an overbroad rule. A stronger one may follow it perfectly. That means an instruction written to compensate for an older model can become friction in a newer one. Upgrading the model without auditing its instructions preserves old weaknesses as permanent policy inside the new system.

The model got better. Your prompt stack did not.

Every failure leaves a fossil

Software accumulates technical debt when yesterday's local workaround becomes tomorrow's architectural constraint. Agent instructions accumulate the same way.

Imagine that an older coding model routinely forgot to verify its changes. You add:

``text Always run the entire test suite after every change. ``

At the time, that may improve reliability. A year later, the model already identifies affected tests and verifies its work, but the instruction remains. Now a one-word copy fix can trigger twenty minutes of integration testing. Nothing is malfunctioning, and the agent is following your repository correctly. The problem is that an old behavioral compensation has been promoted into permanent engineering policy.

That is prompt debt.

A rule solves a real problem. The problem disappears. The rule survives.

Skills have a routing cost before they have an execution cost

Skills look cheap because their full contents are loaded only when needed. The Agent Skills format describes progressive disclosure as loading a skill's name and description first, then the full file only when a task matches.

But before the model can decide which skill it needs, it has to recognize the available choices, which means skill names and descriptions already compete for attention.

Consider a repository with separate skills for:

  • database migrations
  • PostgreSQL
  • schema design
  • backend persistence
  • query performance
  • recovery

Now give each one a description like:

Use this for database work, SQL, migrations, schemas, queries, persistence, models, storage, or backend operations.

A simple query change may appear relevant to half the skill library. The agent now has a classification problem before it has a coding problem.

The better pattern is still progressive disclosure. OpenAI's skills documentation makes the same case: the full guidance belongs in supporting files that arrive only when a task needs them.

``text database/ ├── router.md └── references/ ├── migrations.md ├── performance.md └── recovery.md ``

The root file only needs enough information to route the task. For example: schema change leads to migrations.md, slow query to performance.md, restore or data loss to recovery.md. The detailed guidance still exists and simply arrives when the task gives the agent a reason to read it. That is a better use of context than loading operational knowledge speculatively.

AGENTS.md should preserve what code cannot explain

Repository-level instructions are different because they follow the agent into almost every task. Repository files like AGENTS.md load into a session the way Claude Code's memory docs describe: as standing context that shapes each run. That makes them expensive when they are wrong, stale, or unnecessarily broad.

A useful test is:

Would a capable engineer inspecting this repository be able to infer this safely and cheaply?

If yes, the rule may not belong in AGENTS.md; if no, it probably does.

Compare these two instructions. The first is repository-specific knowledge the model may not safely infer:

```text KEEP

Generated API clients in /src/sdk are immutable. Edit the generator source instead. ```

Now compare with a workflow that may make sense for an architectural refactor but does not for a one-word typo fix:

```text MOVE OR REMOVE

Before making any change: 1. Read ARCHITECTURE.md 2. Inspect the repository map 3. Review all package documentation 4. Identify downstream dependencies ```

Persistent instructions should mostly encode three things: invariants that must remain true, hidden constraints the codebase does not make obvious, and autonomy boundaries where the agent may proceed and where it genuinely needs a human decision. That is a much narrower job than teaching the model how to perform software engineering.

Better models make permission more important

Stronger instruction following creates a less obvious failure mode. The agent can respect your boundaries so carefully that it stops where you expected it to continue.

Suppose it implements a change and one affected local test fails because of that implementation. It replies: auth_spec.ts is failing. Should I fix it?

The model knows how to repair the test, but it does not know whether the repair belongs inside the authority you gave it. This is where a permission grant is more useful than another procedure.

```text Local tests use disposable fixtures and have no production access.

Run affected tests, fix regressions caused by the requested change, and rerun them without asking for approval at each step. ```

That tells the agent three things it cannot necessarily infer: the environment is safe, remediation is within scope, and it is allowed to continue. This produces a more useful decision boundary than blanket rules such as "never expand scope."

A practical ownership map looks like this:

| Human approval | Agent can usually continue | | --- | --- | | Delete production data | Fix a test broken by its own change | | Change authentication policy | Update nearby local types | | Break a public API contract | Format modified files | | Introduce a migration with operational risk | Rerun affected local tests |

The distinction is consequence. Not every adjacent action deserves the same approval boundary.

Define completion before procedure

Old-style prompts often describe the path:

``text Read these files. Modify these modules. Run this command. Inspect this output. Run these tests. ``

That can help when the workflow is genuinely fragile, but a capable agent often benefits more from a clear endpoint.

Compare Implement the avatar endpoint. with:

```text Implement the avatar endpoint.

Run the affected local tests, inspect the returned payload, fix regressions caused by this change, and stop when the requested behavior works or an external blocker requires a decision from me. ```

The second prompt does not tell the model which file to inspect first. It tells the model what finished means. That distinction becomes more important as models gain enough judgment to choose their own path through a repository. The human sets the destination and the dangerous edges, and the agent handles the route.

The instruction hierarchy should be intentional

A clean agent setup separates three layers.

```text AGENTS.md ↓ Repository invariants Safety boundaries Global permissions

Skills ↓ Specialized workflows Loaded only when relevant

Task prompt ↓ Immediate objective Local constraints Definition of done ```

Problems appear when these layers collapse into each other. A one-off task workflow gets promoted into AGENTS.md, a global safety rule gets buried inside a skill the model may never load, a skill becomes an encyclopedia, and a task prompt repeats repository knowledge the model already has. The more capable the model becomes, the more expensive that duplication can become.

Audit prompt debt whenever the model changes

A model upgrade should trigger an instruction audit. The trigger is not that every old instruction is wrong; the assumptions behind them may simply have changed. A useful audit is four passes.

Inventory historical compensations

Gather the instructions that shape agent behavior:

  • AGENTS.md
  • skill descriptions
  • skill bodies
  • system-level repository prompts
  • repeated task-template instructions

For each rule, identify why it exists and what failure originally caused someone to write it.

Separate invariants from rituals

Ask whether a capable engineer could infer this safely and cheaply from the repository. If yes, test whether the rule can be removed; if no, preserve it. Especially keep rules involving production risk, generated artifacts, hidden infrastructure behavior, and non-obvious operational constraints.

Turn heavy skills into routers

If a skill covers several workflows, make the entry point small. Load migration instructions only for migrations, recovery procedures only when recovery is relevant. Keep the specialized knowledge without forcing all of it into every nearby task.

Review prohibitions as decision boundaries

Rules like NEVER touch X, ALWAYS ask before Y, and ONLY modify Z may still be correct, but inspect the consequence they are protecting. Sometimes the better rule is that you may modify X during local development and ask before changing X in production, or you may fix regressions introduced by your own change and ask before expanding into unrelated behavior.

The goal is not maximal autonomy. The goal is to put human attention where the consequences justify it.

What should survive every upgrade

Some instructions should remain even as models improve. A deployment may require an undocumented legacy flag, generated files may look editable even though changes will be overwritten, a local environment may resemble production while using disposable fixtures, and a migration may need compatibility across two running application versions. Those are high-value instructions because intelligence alone does not reveal them reliably.

The useful filter is information value. If the instruction captures something the model cannot safely discover, keep it. If it merely describes how an older model needed to be walked through an ordinary engineering task, reconsider it. Prompt debt does not come from having many instructions. It comes from instructions whose original purpose has expired.

The old approach to coding agents was to describe more of the route. As the models get better, the more useful architecture is becoming simpler: preserve the invariants, define the permissions, and specify what done means. Then let the agent work out the middle, and when the next model arrives, audit the rules before adding new ones.
