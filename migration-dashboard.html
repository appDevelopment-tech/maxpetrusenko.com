The Agent That Watches Everything

Three layers of "is it working?" — from inside-out.

Layer 1: App Self-Report (Inside the Container)

Your social-poster exposes GET /status that returns JSON: last success time per job, next scheduled run, last error per vendor, queue depth. This is what YOU check when you want a quick glance. Hit social.maxpetrusenko.com/status from your phone.

Layer 2: Host Monitor (Netdata on VPS)

Netdata runs as a separate container, auto-discovers all running services, tracks CPU/RAM/disk/swap/network per container. Alerts to Slack when Chromium eats all your RAM (it will). This catches infrastructure problems the app can't see about itself.

Layer 3: External Uptime (UptimeRobot / Better Stack)

Runs OUTSIDE your VPS. Pings /health every 60 seconds. If your entire VPS goes down, Netdata can't tell you because it's also down. This external check catches that. Sends Slack DM + email. Free tier is enough.

Layer 4: Slack Aggregation (Your Single Pane)

Everything reports to one Slack channel: #infra-alerts. Social-poster sends "posted to X at 11:02 AM" confirmations. Netdata sends "RAM > 80%" warnings. UptimeRobot sends "site down" alerts. One channel to check = one source of truth for "is it working?"

What about the Claude agent from Downloads/claw-code?

That agent was solving the wrong problem. You were using Claude as infrastructure (scheduling, monitoring) because you didn't have always-on infrastructure. Once social-poster runs on Contabo 24/7, you don't need an agent to "check if posts are working." The /status endpoint + Slack alerts do that. Claude goes back to being your dev assistant, not your cron daemon.

What Others Do (Research)

Patterns from devs who've done this consolidation.

Pattern 1: One VPS + Coolify = Your Own Heroku

The dominant 2025-2026 pattern for solo devs: one beefy VPS ($10-30/mo), Coolify as PaaS layer, Git push to deploy. Replaces the "scripts on my laptop" problem entirely. Static sites stay on Cloudflare Pages (free), compute-heavy stuff goes to the VPS. You're already on this path.

Sources: coolify.io, dev.to, digitalocean.com, criztec.com

Pattern 2: Monitoring = 3 Layers (Not 1)

Every production setup that works uses at minimum: (1) app-level health endpoints, (2) host-level metrics (Netdata, node-exporter + Grafana), (3) external uptime check from a different network. The mistake most solo devs make is only having #1, which can't detect if the whole box dies.

Sources: peturgeorgievv.com, uptimerobot.com, rapidinnovation.io

Pattern 3: "Deploy Fast" = Git Push, Nothing Else

The simplest update path: push to main, Coolify auto-builds and deploys via webhook. Health check must pass before traffic routes. If it fails, auto-rollback to previous. Zero SSH, zero manual docker commands. The Dockerfile IS the deploy spec.

Sources: dev.to/matthewh, dev.to/lucasnevespereira

Pattern 4: Secrets in Doppler/Vault, Not in Repos or .env

Your migration plan already calls this out. Doppler syncs to Coolify env vars. No secrets in git, no secrets in docs. Rotate anything that was ever in plaintext (your earlier draft had inline keys).

Sources: doppler.com, your migration plan (correction section)

Pattern 5: Don't Use AI Agents as Infrastructure

Using Claude/Codex/agents as cron schedulers or monitoring agents is a common early pattern that breaks at scale. The agent should write and improve the code; the server should run it. "Agent manages and lets me know" = /status endpoint + Slack webhook, not a Claude loop.

Sources: sundayguardianlive.com (OpenClaw analysis), openobserve.ai
